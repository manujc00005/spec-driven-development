# Context Manager

## Purpose

Produce a **bounded reading list** — the minimum set of files Claude needs to load into context
before acting on the current feature. This avoids full-repo scans on large codebases (especially
multi-module Java/Spring microservices) and keeps token usage proportional to feature scope.

## Inputs

1. **Active spec** — `specs/features/<NNN>/SPEC.md` (required).
2. **Context docs** (read if they exist, skip gracefully if absent):
   - `docs/PROJECT_CONTEXT.md`
   - `docs/TECH_STACK.md`
   - `docs/ARCHITECTURE.md`
3. **Graph map** (optional accelerator):
   - Resolved in this order: `.graphify/GRAPH_REPORT.md` (canonical — where the
     Graphify CLI writes it), then `GRAPH_REPORT.md` at project root (legacy
     fallback). If both exist, `.graphify/` wins.
   - If present **and fresh**, use it to identify impacted modules.
   - If absent or stale, fall back to bounded heuristic scan.
4. **PLAN.md / TASKS.md** — to understand which task is active.

## Behavior

**Graph-first doctrine (token saving):** when the graph map exists, derive the
reading list from it BEFORE any repo-wide Glob/Grep/Read sweep. The heuristic
scan is the explicit fallback, never the default.

1. **Ask the graph first — by query, not by reading the report:**
   - When the `graphify` CLI is on PATH, this is the cheapest and most direct path:
     `graphify review-context <file>` and `graphify affected-flows <file>` return
     exactly the bounded list this skill exists to produce, and
     `graphify summary` orients across the whole graph for ~350 tokens.
     They read `graph.json` inside the CLI process, so the model never pays for it.
   - **Reading `.graphify/GRAPH_REPORT.md` in full is the fallback**, used when the
     CLI is unavailable or a query cannot answer the question — measured at ~7.101
     tokens against ~354 for `summary` on the same graph. See
     `skills/graphify-context/SKILL.md` for the full access ladder.
   - Check staleness before trusting either path: a query on a stale graph is cheap
     and wrong.
   - If no graph is usable at all: note it and proceed with the heuristic fallback.
2. **Read context docs** (if they exist) to understand boundaries, modules, and communication patterns.
3. **Read the active spec** — extract impacted domains, endpoints, entities, events, and data stores.
4. **Heuristic fallback** (only when no usable graph map):
   - From the spec's declared changes (API, data model, messaging), infer which packages/directories
     are likely impacted.
   - Limit to at most **15 files** for initial context load.
5. **Output the reading list:**
   - Ordered by relevance (most impacted first).
   - Each entry: file path + one-line reason why it's relevant.
   - Clearly marked: "Read these before implementing. Skip everything else unless a finding points there."
6. **Cache the list** in `DECISIONS.md` of the active feature (under a `## Context reading list` section)
   so re-entry to the same feature doesn't re-derive it.

## Output format

```markdown
## Context reading list

Generated by /context-manager for spec NNN-feature-name.

| # | File | Reason |
|---|---|---|
| 1 | `src/main/java/.../OrderService.java` | Service containing the affected business logic |
| 2 | ... | ... |

**Graph map status:** fresh / stale (N days) / absent
**Fallback used:** yes / no
```

## Graceful degradation

- No `docs/PROJECT_CONTEXT.md` → skip; note "project context not available, scanning broader".
- No Graphify report (neither `.graphify/GRAPH_REPORT.md` nor legacy root `GRAPH_REPORT.md`) → use heuristic; note "Graphify map not available — run scripts/setup-graphify.sh for better precision and lower token usage".
- No `PLAN.md` yet → use SPEC.md alone.

## What this skill does NOT do

- Does not run Graphify (that's `graphify-context`).
- Does not modify application code.
- Does not replace reading the actual files — it only decides *which* files to read.
- Does not block on missing context docs — always produces a best-effort list.
